# ReStroke

> Recover the Drawing Process.

完成したイラストや写真を解析し、人の手で描いたときの工程を推定してタイムラプス動画を生成します。

**実際の制作過程を復元するものではありません。** 完成画像には時間の情報が残っていないため、
本アプリが行うのは「自然な制作過程を組み立てて再現すること」です。

長さをどう設定しても、**最後のフレームは元画像と完全に一致**します（全画素が一致することを
確認済み）。別の画像を後から重ねるのではなく、仕上げの筆が元画像そのものを絵の具にして
塗り切るためです。

---

## 使い方

```bash
npm install
npm run dev
```

ブラウザで `http://localhost:5173` が開きます。

1. 画像をドロップ（PNG / JPEG / WebP・最大 8192 × 8192）
2. 画風・長さ・出力設定を選ぶ
3. **解析して生成** を押す
4. 再生を確認して **書き出す**

テストは以下で実行します。

```bash
npm test
```

型チェックとテストをまとめて走らせるなら `npm run check`。

解析・生成・書き出しはすべてブラウザ内で完結し、画像が外部へ送信されることはありません。
サーバも外部 API も使いません。

本番用のビルドは `npm run build`（出力先 `dist/`）。生成物は静的ファイルのみです。

## 処理の流れ

```
画像
 ↓ 前処理        縮小・平滑化・輝度化
 ↓ 輪郭抽出      Sobel 勾配 → 稜線追跡で線の軌跡を取り出す
 ↓ 色解析        色ヒストグラム上の中央値分割で代表色を決める
 ↓ 領域分割      同じ代表色でつながった画素の塊を求める
 ↓ レイヤー推定  面積・明るさから工程へ割り当てる
 ↓ 描画順推定    ラフ → 線画 → 着色（ベース → 影 → 光 → 細部）→ 仕上げ
 ↓ ストローク生成 領域の主軸に沿った走査でベジェ曲線の筆運びへ変換
 ↓ 動画生成      離散時間の状態遷移として再生し、フレームを記録
```

### 工程

| 工程 | 内容 |
| --- | --- |
| ラフ | 形を探る当たり線だけを引く。色はまだ置かない |
| 線画 | 輪郭をたどって得た軌跡を、1 本ずつ引いていく |
| ベースカラー | 下塗りで全体に色を入れ、広い面から順に塗る |
| 影 / 光 | 暗い領域・明るい領域を、にじむ筆で重ねる |
| 細部 | 小さな色の塊と、輪郭沿いの短い筆 |
| 仕上げ | **残りの予算をすべて使い、元画像を絵の具にした筆で詰め切る** |

背景は独立した工程を持ちません。広い面も 1 つの色の領域として、下塗りと
ベースカラーが引き受けます。

下塗りは**すでに引いた線の下へ潜り込ませる**ので、線画が塗りで消えません
（描画面を透明で持ち、紙の色は表示時に敷いています）。

### ストロークが持つ情報

```json
{
  "x1": 123, "y1": 455, "x2": 245, "y2": 467,
  "size": 12, "pressure": 0.82, "opacity": 0.91, "time": 12.4
}
```

始点・制御点・終点（2 次ベジェ）、太さ、色、不透明度、筆圧、所属レイヤー、所要時間を
フィールドごとの型付き配列（SoA）で保持します。1 本あたり 40 バイト弱で、
2 万本でも 1MB 未満に収まります。

## 設計の要点

### 決定論的な状態遷移として再生する

再生の実体は、離散時間 tick ごとの純粋な状態遷移です。

```
S(t+1) = F(S(t), 入力(t), 環境(t))
```

- ゆらぎはすべて `(シード, tick, 番号)` から引く**状態を持たないハッシュ**から得ます。
  内部カウンタを進める擬似乱数生成器は使いません。呼ぶ順序が結果を変えてしまうためです。
- 同じ画像・同じシード・同じ設定からは、**常にビット単位で同じ映像**が出ます
  （キャンバスのピクセルを照合して確認済み）。
- 保存する履歴は「規則の版・初期シード・入力列」の 3 点だけで、各時点の絵は保存しません。
  任意の時点へは記録から計算し直して到達します。
- **工程データ**（JSON）はこの履歴そのものです。書き出して読み込み直すと画風・長さ・種・
  設定が復元され、同じ画像からまったく同じタイムラプスが組み立て直されます
  （復元した種は `#4d37984a` のような 16 進表記で種の欄に入ります）。
  規則の版が変わっている工程データは、同じ結果にならないため読み込みを断ります。

### 軽量化

- 解析は縮小した作業画像（長辺 1152px 以下）の上で行う
- 前に進むときは**その tick で伸びた区間だけ**を描き足す。全面の描き直しをしない
- 巻き戻し用に途中経過を 8 点キャッシュする。これは速度のためだけの派生物で、
  捨てても結果は変わらない
- ストローク総数に上限を設け、超えた場合は筆の間隔を広げて作り直す
  （1 本を太く粗くすることで、どんな画像でも決まった予算に収める）
- 画面が重いときは**画面への転送だけ**を間引く。描かれる内容は変えない

> 実測（640 × 440 の画像・出力 1080px・30 秒・粒度レベル 6）:
> 解析と生成が 0.2〜0.6 秒、ストローク 5.6 万本。全ストロークを先頭から描き直しても
> 0.1〜0.2 秒で、30 秒の再生に対して十分な余裕があります。

### 解析の粒度

レベル 1〜10 で指定します。1 つ上げると、解析解像度・代表色数・線の拾い方・筆の細かさ・
本数の上限がまとめて上がります。

| レベル | 解析解像度 | 本数の上限 | 目安 |
| --- | --- | --- | --- |
| 1 | 640px | 0.9 万 | 筆致を大きく残す |
| 4 | 1013px | 2.7 万 | 軽い |
| 6 | 1262px | 5.6 万 | 標準 |
| 8 | 1511px | 11.6 万 | 細かい |
| 10 | 1760px | 24.0 万 | 最も細かい |

粒度に関わる値は [quality.ts](src/analysis/quality.ts) の 1 か所にまとめてあります。

### 最後を必ず元画像に合わせる

**元画像そのものを絵の具にする**、という一点で解決しています。仕上げの筆は単色ではなく、
出力解像度に合わせた元画像を模様として乗せて引きます。筆が通ったところには元の画素が
そのまま置かれるので、塗り重ねるだけで最後は元画像と一致します。別の絵を後から重ねる
処理はありません。

置く順番は「まだ情報が足りていないところ」＝輪郭が強く、周囲との色の差が大きいところから。
ただし優先度どおりに並べると画面を上から順に舐める動きになるため、網の目を 16 層に分け、
全体をうっすら詰めてから密度を上げていきます。絵全体が同時に鮮明になっていくように見えます。

最後は画面と同じ高さの筆でひと息に通します。細い筆だけで仕上げると、筆の縁（ぼかしの
かかる部分）が 8bit の丸めで 1 段階ずれたまま残ることがあるためです。大きな筆なら全画素が
筆の内側に入るので、ずれが残りません。同じ理由で、仕上げの筆は**引き終わってから一筆で
置きます**（途中で切って継ぎ足すと、継ぎ目に縁が重なってずれます）。

この時点で画面はすでにほぼ元画像なので、見た目には何も起きていないように見えます。

工程ごとの持ち時間には終わりに 12%（最大 24 tick）の余裕を残してあり、ゆらぎや一息で
遅れてもその中で追いつきます。「最後の 1 フレームで一気に完成する」ことはありません。

### 「絵を決めるもの」と「見せ方」を分ける

フレーム時間や表示中のカメラ位置といった実行時の計測値を工程の判断に使うと、
同じ入力から違う動画が出てしまいます。そのため、

- **絵を決める適応**（筆の間隔、工程の時間配分、ペース配分）は、確定した状態とシードのみから決める
- **見せ方の適応**（画面への転送頻度、プレビューの縮小）は実測値に依存してよいが、絵は変えない

という区分を守っています。レイヤーの表示切り替えも同じ考え方で、
表示から外しても工程そのものは変わりません。

## 構成

```
src/
  core/        状態遷移・動態モデル・履歴・スキーマ・エンジン
  analysis/    前処理・輪郭抽出・色解析・領域分割・レイヤー推定
  strokes/     画風プリセット・ストローク生成
  render/      キャンバス描画・描画面の生成
  export/      動画録画・GIF エンコーダ（外部ライブラリなし）
  main.ts      画面
tests/
  core/ analysis/ strokes/ render/ export/
  integration.test.ts   画像を入れてから最終フレームまでの通し確認
  helpers/              テスト用の画像・描画面・GIF 読み取り
```

ランタイム依存はゼロです（開発時のみ Vite・TypeScript・Vitest を使用）。

## 制約と既知の限界

- **正確な描画順は復元できません。** 完成画像に時間情報がないため、すべて推定です。
- 仕上げの筆は元画像を絵の具にするため、この工程だけは筆致というより「元の絵が現れてくる」
  見え方になります。途中の筆致だけを見たい場合は、仕上げレイヤーの表示を外してください。
- 解析の粒度を上げるとストローク数が増え、解析・生成の時間と使用メモリが増えます。
  レベル 10 では 20 万本を超えることがあります。
- レイヤーは色と明るさから機械的に分けたもので、意味（髪・目・服など）は判別しません。
- 動画の書き出しは再生しながら記録するため、指定した長さと同じだけ時間がかかります。
  GIF は待ち時間なしで書き出せますが、256 色・12fps・長辺 480px に落とされます。
- MP4 が選べるかはブラウザの対応状況によります（選べない場合は WebM を使用）。
- 極端に粒状な画像は、細かい塊に砕けて筆致が細かくなりすぎることがあります。
  「筆致の細かさ」を粗い側にすると安定します。
